## 7. C++ coding-lab implementation

The editor provides CODE (`main.cpp`), Program Input, Run, Stop, Reset, Clear, Copy Code, and Save Code. Program output, compiler diagnostics, and runtime messages appear separately. Teacher review also includes the runnable source with editable test input.

The optional **Check against example samples** checkbox compares compiled behavior on sample inputs and normalizes harmless whitespace. It applies to the lesson example rather than assuming the independent activity must print the same output. Teachers can edit these test cases through existing validation-rules content management. Variable names and exact source text are not grading criteria. Browser checks cannot mark a lesson complete.

## 8. Compiler/sandbox implementation

Clang 22.1.8 and its linker run as WebAssembly inside a fresh worker hosted by an opaque `sandbox="allow-scripts"` iframe. Fixed flags select strict C++17, warnings, and standard WebAssembly exception handling. WASI SDK 33 provides matching exception-enabled libc++, libc++abi, and libunwind, so `try`/`throw`/`catch` work along with `fstream`, STL, and smart pointers.

The build pins `@live-codes/clang-wasm` 0.3.0 and `@noble/hashes` 2.0.1. It verifies the official SDK archive against SHA-256 `063bc1b56582b9923e08ac9b89e58789618d851763f01530b3ff20b9e5df0ca3`. The SHA-256 fallback supports compiler fingerprints inside an opaque origin without giving the iframe the Laravel origin. Generated notices retain upstream attribution and describe the memory modification.

Compiler sources: [Clang WASM project](https://github.com/live-codes/clang-wasm), [official WASI SDK 33](https://github.com/WebAssembly/wasi-sdk/releases/tag/wasi-sdk-33), and [official exception-support notes](https://github.com/WebAssembly/wasi-sdk/blob/main/CppExceptions.md).

## 9. Standard-input handling

Source and input are saved together and snapshotted on submission; changing input invalidates an older pending review just like changing source.

## 13. Security protections

- Student source is compiled/executed only as browser WebAssembly, never through Laravel shell/process functions or native compiler execution.
- The guest imports only a synthetic WASI host with empty environment information except its virtual working directory. No production files, PHP environment, database passwords, browser cookies, or application credentials are mounted.
- Every execution starts with a fresh virtual filesystem. Only temporary teaching files are available; code cannot read the compiler's virtual sysroot during program execution.
- No guest process spawning, native shell, network, threads, or external service credentials are exposed. Worker networking is disabled before guest execution; asset fetching uses the fixed local runtime endpoints.
- Parent-owned deadlines terminate the worker: loading 90 seconds, compilation 30 seconds, execution 5 seconds per run/test. There is one worker per editor run, with no student-created process pool. Stop and page cleanup release the worker.
- Program linear memory is capped at 64 MiB by the linker. Compiler, linker, and memfs WASM memories each have a hard 256 MiB ceiling. These are WASM limits; browser/JavaScript bookkeeping consumes additional memory.
- Source/input limits are 200,000/20,000 characters. Combined stdout/stderr is bounded at 64 KiB. Virtual file sizes and cumulative allocations are limited to 1 MiB, including sparse-file seeks and explicit allocation/truncation. Write and filesystem-operation counts are bounded.
- Runtime asset routes allow only named build artifacts. `.env`, arbitrary source paths, and POST execution requests are denied. Education-level access, publication, gating, version checks, quiz scoring, teacher approval, and rubric bounds are enforced on the server.

## 15. Remaining limitations or placeholders

The compiler is functional and locally hosted; no external compiler account/key is required. This is an educational C++17/WASI runtime rather than a full native desktop OS. It does not expose threads, native networking, GUI libraries, arbitrary system commands, or platform-specific libraries. Modern browsers must support WebAssembly exception handling and have enough memory for the compiler; the first run downloads roughly 30 MB of runtime assets.

Files persist only within one Run. Demonstrate save/load in the same run; durable project file storage is not implemented. The browser editor accepts one `main.cpp`; the advanced project teaches a native multi-file organization using logical sections and a suggested file map. Interactive input after execution begins is not implemented; supply complete stdin up front. Wall-clock termination is enforced by the browser, not an OS/container CPU quota.

Automatic sample checks are practice feedback, not a tamper-proof grading service or hidden-test system. Teachers verify activity logic and concepts before approval. This preserves the existing review model and permits valid alternative solutions. No production deployment was performed. Existing build-tool audit advisories were not resolved by unrelated dependency upgrades.
